# 《灵域天空岛》系统设计案例：生产 · 物流 · 存储

| 项 | 内容 |
|---|---|
| 项目 | 2D 沙盒自动化同人独立游戏 |
| 角色 | 策划负责人（系统设计与文档落地） |
| 时间 | 2025.09 – 至今 |
| 本文定位 | **模块划界与通用规则**的公开精炼版（非完整内部 GDD） |

---

## 1. 背景与设计问题

沙盒自动化品类容易把「建造乐趣」做成「堆料与微操带速」。本项目希望玩家的长期乐趣落在：

- **产能是否匹配**
- **配方与设施如何组合**
- **堵塞时如何读懂并调控**

因此需要先回答三个系统问题：

1. **生产 / 物流 / 存储各自负责什么？** 边界不清会导致规则打架、程序难落地、玩家学不会。  
2. **自动化成长如何从手工过渡？** 既要前期可玩，又要中后期产线成立。  
3. **失配如何反馈？** 不用「传送带科技等级」制造假深度，而用可读的堵塞与反压。

---

## 2. 解法总览：先划界，再写规则

| 系统 | 本质职责 | 不做的事 |
|---|---|---|
| **生产** | **物品转换**（配方、时序、停工） | 不负责长距离搬运；输入口不是普通仓库格 |
| **物流** | **搬运与反压**（通路、缓冲、堵塞信号） | 不改变物品种类；不设独立带速瓶颈 |
| **存储** | **保管与界面管理**（不转换） | 不执行配方；接物流后端口仍不转化物品 |

一句话：**生产改物品，物流移物品，存储管物品。**

```text
采集 / 加工设施 ──产出──▶ 物流通路（单格缓冲）──▶ 下游设施 / 容器
         ▲ 反压停工 ◀── 缓冲满 / 下游拒收
```

---

## 3. 生产系统：统一转换骨架

### 3.1 设计目的

1. 所有生产设施共用一套**配方 · 端口 · 时序 · 停工**骨架，差异尽量进配置。  
2. 支撑「近身手工 → 持续中间件 → 指定总装」的成长。  
3. 工业量产与玩家少量成品需求用同一规则、不同用法解决。

### 3.2 关键规则（摘录）

- **输入口容量 = 当前配方该槽单次用量**（不是堆叠上限）；未选配方则拒绝输入。  
- **持续生产**：条件满足则反复执行（适合中间件）。  
- **指定生产**：剩余次数耗尽后停工（适合装备/设备本体）。  
- **停工状态机**统一承接：缺料、输出受阻、次数用尽等；与物流反压对接。

### 3.3 取舍

- **取：** 大类共用 UI/规则，等级只改速率、配方权限、端口数等配置 → 利于扩展与程序对接。  
- **舍：** 本文公开版不展开各大类细则清单；内部案中未完成条目不进入求职材料，避免「半成品文档感」。

---

## 4. 物流系统：产能匹配优先

### 4.1 设计目的

1. 用拖拽连接把产线节点变成**可视、可调**的物资流。  
2. 策略重心放在**上下游匹配**，而不是微操带速。  
3. 堵塞必须**可读、可解**：缓冲满 → 通路变红 → 上游停工 → 玩家可取出缓冲物解除反压。

### 4.2 关键规则（摘录）

- 仅允许 **输出口 → 输入口**；一条通路 **一带一种物品**。  
- 通路含 **单格缓冲**，上限对齐存储单格堆叠上限。  
- **不设独立额定带速**；畅通时速率跟随可匹配的上下游。  
- 缓冲顶满触发**反压**，与生产停工状态机对接。

### 4.3 取舍

- **取：** 「通路 ≈ 自动写入/读出的单格箱」降低学习成本，和存储直觉一致。  
- **舍（本版不做）：** 跨岛仙台、大型多口传送仓库等远期能力只作预留，不写进当前验收范围。

---

## 5. 存储系统：不转换的保管层

### 5.1 定位

存储只做**保管与操作界面**（储物袋 / 固定容器的选中、半选、交换等）。  
与生产的硬界限：

| | 存储容器 | 生产设施 |
|---|---|---|
| 本质 | 不转换 | 发生转换（配方） |
| 口/格容量 | 堆叠上限（接物流后端口同理） | 输入口 = 单次配方用量 |

### 5.2 取舍

- **取：** UI 细则可独立打磨，不阻塞产线规则冻结。  
- **舍：** 多口仓库、跨界大型传送仓储等与物流远期接口合并规划，避免命名与系统职责混淆。

---

## 6. 三系统如何互相证明设计能力

| 能力点 | 在本案例中的落点 |
|---|---|
| 模块边界 | 转换 / 搬运 / 保管三分法，表格可评审 |
| 体验目标对齐 | 用反压与停工服务「产能匹配」，而非带速养成 |
| 可扩展性 | 生产大类配置化；物流基础分流/筛选可后续加，不破坏主规则 |
| 可落地性 | 端口语义统一为「受约束单格」；规则可对接配置表字段 |
